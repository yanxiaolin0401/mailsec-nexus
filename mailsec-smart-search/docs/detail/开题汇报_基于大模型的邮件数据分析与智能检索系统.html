📋 1. 核心邮件头（Headers）IETF RFC 官方定义与解析关注点
标准邮件头 (RFC规范) IETF RFC 官方规范定义 工程解析与安全关注点
Received
RFC 5322 §3.6.7
RFC 5321 §4.4 (Trace) 		传输追踪字段（Trace Field）
由传输代理 (MTA) 逐跳在顶部追加，记录中继节点、客户端主机标识及接收时间戳。		 逆向回溯投递链路；最靠近收件端的外部边界网关记录，用于提取真实公网来源 IP。
Authentication-Results
RFC 8601 (Message Auth) 		消息认证状态头
记录边界接收网关对邮件执行 SPF、DKIM、DMARC 密码学与源地址校验的综合判定结论。		 提取结构化认证结论（如 spf=fail、dkim=none），作为发件人仿冒与域欺诈判定的核心依据。
From
RFC 5322 §3.6.2 (Originator) 		消息始发者邮箱（Author Mailbox）
指定对编写该消息负责的实体（人或系统）的邮箱地址。		 属于应用层显示头，极易被信封伪造；需提取纯域名并与 Received 来源 IP 交叉比对。
To / Cc
RFC 5322 §3.6.3 (Destination) 		目标接收者列表（Destinations）
To 指定主要收件人，Cc 指定抄送（Carbon Copy）感兴趣方的收件人列表。		 结构化拆解为数组入库，用于审计收件范围、识别异常大批量群发或无收件人隐匿行为。
Date / Subject
RFC 5322 §3.6.1 / §3.6.5 		发端时间戳与主题摘要
Date 标识消息创建就绪时间；Subject 提供简要概述消息核心内容的文本描述。		 Date 作为时序主轴与 ClickHouse 按月分区键；Subject 需执行 RFC 2047 字符集转码。
Message-ID
RFC 5322 §3.6.4 (Identifier) 		全局消息唯一标识符
用于在机器层面全局唯一标识该邮件特定版本的格式化字符串 <id@domain>。		 作为入库全局去重键与日志关联索引，防止同一封邮件重复写入或循环投递。
Content-Type
RFC 2045 §5 (MIME Headers) 		媒体类型与编码规范描述
声明正文数据类型（Type/Subtype）、字符集编码（charset）及多部分分段标界（boundary）。		 指导解析器流式构建 MIME 树；提取附件文件名与分段 boundary，防范嵌套递归栈溢出。
📦 2. 邮件体（Body）的常见 MIME 形态
  • 单部分纯文本（text/plain 或 text/html）：
    邮件无附件、无备选视图，正文直接位于头后空行下方，通常经 Quoted-Printable 或 Base64 编码。
  • 多部分替代（multipart/alternative）：
    一封邮件内同时提供纯文本与 HTML 两个版本，客户端根据能力选其一渲染。解析时应优先提取纯文本。
  • 多部分混合（multipart/mixed）：
    正文与独立附件的组合形式。每个 Part 用 boundary 隔离，附件 Part 带有 Content-Disposition: attachment; filename="..."。
  • 多部分内嵌关联（multipart/related）：
    正文中内嵌图片、签名等资源（通过 cid:xxx 关联引用）。

Data Architecture
三、 ClickHouse 表结构与高性能存储设计
面向列式存储特性设计，单引擎满足海量多维统计与检索
引擎选型：ClickHouse 单引擎
CREATE TABLE mail_records ( mail_id String, -- 邮件唯一ID (Message-ID/MD5) send_time DateTime, -- 发送时间 (时序主轴) client_ip IPv4, -- 溯源公网IP (从Received解析) from_addr LowCardinality(String), -- 发件人地址 from_domain LowCardinality(String), -- 发件域名 (按域统计) to_addrs Array(String), -- 收件人列表 subject String, -- 邮件主题 body_text String, -- 清洗后的纯文本正文 has_attachment UInt8, -- 是否含附件 (0/1) attachment_names Array(String), -- 附件名列表 attachment_hashes Array(String), -- 附件哈希 (SHA256/MD5) spf_result LowCardinality(String), -- pass / fail / none raw_headers String -- 原始头留存 (供LLM分析) ) ENGINE = MergeTree() PARTITION BY toYYYYMM(send_time) -- 推荐按月分区 ORDER BY (send_time, from_domain, mail_id);
⚡ 存储与写入优化要点
  • 合理的分区策略（Partitioning）：
    推荐采用 toYYYYMM(send_time) 按月分区。过滤时间范围时能直接跳过整月数据分区，检索速度提升数十倍。
  • 批量写入（Batch Insert）缓冲机制：
    ClickHouse 最忌讳单条频繁写入！必须在后台设计写入缓冲区（如累计 2000 条或满 2 秒执行一次批量 INSERT），避免产生大量小部件（Parts）写崩数据库。
  • 低基数字典优化：
    域名、SPF 状态等字段使用 LowCardinality，大幅提升压缩比与过滤效率。

🛡️ 2. 接口超时重传与降级保护

工业级系统严禁“裸调”外部大模型 API，必须内置网络防御机制：

  • 硬超时截断（Timeout）：单次请求设置硬超时阈值（如 15 秒），拒绝网络拥塞时无休止挂起主线程；
  • 指数退避重传（Retry）：遭遇网络抖动、429 速率限制或 500 远端错误时，自动触发重试机制（如最多重传 2 次）；
  • 优雅降级兜底（Fallback）：当远端模型服务不可用时，系统平稳降级并返回友好默认提示，严禁引发主进程崩溃或影响底层检索核心功能；
  • 凭证安全红线：代码仓库与提交记录中绝对禁止硬编码 API Key，必须通过系统环境变量或未纳入版本控制的本地配置文件注入。

AI Features & SOP
五、 大模型核心应用场景与排查 SOP
赋能自然语言检索，并将常见威胁分析固化为自动化排查流水线
功能设计：恶意研判 · NL2Query · 场景SOP
🎯 核心应用场景与指定功能

🔹 功能 A：恶意邮件判定与威胁研判

提取邮件发信域、正文纯文本摘要、发信路径真实性与可疑附件/链接特征，大模型输出标准化的结构化 JSON：明确给出风险等级（正常/可疑/恶意）、判定依据与识别到的具体攻击手法（如高仿发信人、社工引诱话术、诱饵附件）。

🔹 功能 B：智能自然语言检索 (NL2Query)

运维人员输入日常自然语言（如“查询上周来自财务部门且带有发票附件的邮件”），大模型负责理解业务语义，将其翻译生成 Elasticsearch 查询语句 (Query DSL) 或 ClickHouse SQL；亦可由后端服务直接执行生成的语句，向用户秒级返回匹配结果。

⚡ 功能 C：常用查询排查 SOP（标准作业程序）

· 什么是 SOP：
即 Standard Operating Procedure（标准作业程序）。在网络安全与邮件分析中，SOP 是指将一线分析师高频、套路化的研判工作固化为“一键排查剧本 / 预置分析模板”。

· 典型场景剧本：
1. “财务/发票补贴钓鱼排查 SOP”：组合过滤发件域不匹配 + 发票关键词 + 危险附件类型；
2. “伪造发信域仿冒溯源 SOP”：检索 spf=fail 异常邮件并聚合来源 IP 频次；
3. “可疑双后缀附件排查 SOP”：拉取并研判 .xlsx.exe 等高危变种样本。

· 具体怎么做：
后台将“多维查询过滤规则”与“针对性大模型分析 Prompt”预置为一条自动化处理流水线。用户在界面/CLI 一键触发该 SOP，系统自动联动执行：【条件初筛 → 检索召回可疑列表 → 大模型批量并行研判 → 结构化输出综合排查处置报告】。

Engineering Standards
六、 工程规范与质量要求
工程标准从第一天就执行，保障代码可复现与工业可用性
日常规范：Git Tag · 单元测试 · 错例台账
📋 核心工程规范要求
  • 版本管理（Git）：各组自建 Git 仓库，提交信息清晰可读；每周里程碑按时打 Git Tag（如 v0.1-w1）；环境必须可复现，锁定依赖清单（requirements.txt / uv.lock）。
  • 测试驱动与样本隔离：每一个解析规则配齐单元测试；测试样本 fixture 目录独立维护，严禁大样本塞进代码主分支；每次改动必须执行全量回归。
  • 一键评测脚本：编写一键执行脚本，批量压测样本集，输出解析成功率、崩溃率与平均吞吐（条/秒）。
  • 错例与异常归档：针对挂死或畸形样本建立台账（样本编号 + 报错根因 + 改进措施），作为后续攻坚输入。
🤖 AI 编程与大模型使用规范

鼓励充分利用 AI 编程工具（如 Claude Code / Cursor / Trae 等）提升开发效率，但必须遵守纪律：

  • 审查后合入：AI 生成的代码必须经组员人工审查、跑通本地测试后方可合入，提交时可注明“AI 辅助生成”；
  • 模型选型不限：运行时调用的大模型类型不限，但业务运行链路必须具备容错保护；
  • 严禁黑盒依赖：答辩时将针对核心解析与架构细节进行提问，学生必须理解自身系统的每一处核心实现。

七、 系统验收标准设计
多维度综合评估：吞吐稳定性 + 分析可解释性 + 工程交付
验收模式：公开集自测 + 导师闭门盲测
🚀 1. 系统吞吐与鲁棒性轨
  • 10 万封公开样本压测：全量入库无卡死、无 OOM（内存溢出）；
  • 企业盲测集冲击（核心）：企业导师将在答辩阶段提供一批闭门盲测样本（含超长头、混淆畸形），直接投递进系统端口，系统稳定解析不崩溃；
  • 检索响应时间：ClickHouse 多条件组合查询保持秒级响应。
🧠 2. 智能分析与可解释性轨
  • 分析可解释性：大模型恶意研判不仅给出正常/可疑标签，必须输出清晰的判定逻辑与证据特征（如域名仿冒证据）；
  • NL2Query 准确性：自然语言转化过滤条件准确，无语法错误；
  • 调用健壮性：网络抖动或大模型响应超时时，自动重试并优雅降级，服务不宕机。

  • 交互友好度：提供直观易用的交互式 CLI 工具或简洁轻量 Web 界面；
  • 扩展性与错例台账：针对异构邮件系统的扩展性设计，错例分析归档详尽。
