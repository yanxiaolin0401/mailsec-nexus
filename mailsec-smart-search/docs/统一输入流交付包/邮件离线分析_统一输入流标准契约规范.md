# 邮件安全离线分析系统 · 统一输入流标准契约规范 (Canonical Ingestion API Spec v2.0)

> **版本**：v2.0 (2026-11)  
> **适用对象**：开发组离线仿真灌库平台。  
> **设计目标**：
> 1. **统一接口与协议**：固化单一输入路由、请求方法与响应状态码，消除各组对接歧义；
> 2. **消除历史技术债**：彻底废除历史样例中以逗号拼接附件、用 JSON 数组字符串存储邮件头（`mailHeaderList`）等脏格式，收敛为强类型、现代化的标准 JSON；
> 3. **无缝衔接仿真语料与测试 Demo**：既完全兼容前期测试样例 (`demo.xlsx`)，又能直接消费由生产真实攻防告警转换而来的标准化脱敏语料 (`mail_offline_dataset_1000.jsonl`)。

---

## 一、 协议与端点定义 (Protocol & Endpoints)

### 1.1 HTTP 接口约定
- **请求方法**：`POST`
- **接口路径**：`/api/v2/mails`
- **报文格式**：`Content-Type: application/json; charset=utf-8`
- **鉴权头标**：`X-Intake-Key: <string>`（测试环境统一使用：`dev-bench-key`，用于标识接入方租户及安全信任边界）
- **负载形态**：支持 **单封邮件对象** (`{...}`) 或 **邮件批量数组** (`[{...}, ...]`)。

### 1.2 状态码与响应语义 (Status Codes)
各组服务必须严格遵守以下 HTTP 响应语义，严禁“无论成败一律返回 200”：

| HTTP 状态码 | 语义说明 | 响应体格式 (JSON) | 触发场景 |
| :--- | :--- | :--- | :--- |
| **`202 Accepted`** | **成功受理** | `{"eventId":"...","sourceSystemId":"...","sourceEventId":"...","status":"accepted","acceptedAt":"..."}` | 邮件已成功通过基本格式校验，并写入本地持久化缓冲（如 G4 SQLite Spool、G1 BatchBuffer、G3 Kafka Broker）。注意：202 表示**排队受理成功**，不代表最终 AI 分析/落库完成。 |
| **`400 Bad Request`** | **请求格式错误** | `{"detail":"Invalid JSON body"}` | 无法解析的 JSON 语法错误、报文截断等。 |
| **`415 Unsupported Media Type`** | **媒体类型错误** | `{"detail":"Content-Type must be application/json"}` | 未携带 `application/json` 请求头。 |
| **`422 Unprocessable Entity`** | **契约校验失败** | `{"detail":"Missing required field: eventTime"}` | 缺失不可或缺的主键或关键字段类型不匹配。 |
| **`503 Service Unavailable`** | **背压与故障** | `{"detail":"Ingest queue full or storage unavailable"}` | 队列已满、Kafka 宕机或 ClickHouse 连接失败。**必须返回 503 告知上游退避重试，严禁丢弃数据**。 |

## 二、 标准请求体结构 (Canonical JSON Schema)

### 2.1 完整字段定义与兜底规范
所有字段禁止出现 `null`（出现 `null` 会导致部分强类型 Pydantic 模型直接抛 422 异常）。字段缺省必须按规范填充默认占位符。

| 字段名称 (CamelCase) | 数据类型 | 必填 | 默认占位值 | 字段说明与规则约束 |
| :--- | :--- | :---: | :---: | :--- |
| **`eventId`** | `string` | 是 | - | 事件全局唯一主键（UUID 格式）。若上游未提供，可通过 `sourceSystemId + sourceEventId` 生成 UUID5。 |
| **`sourceSystemId`** | `string` | 是 | `MAIL_OFFLINE` | 数据来源系统标识（如 `MAIL_ES_MSS`、`MAIL_DEMO_EXCEL`）。 |
| **`sourceEventId`** | `string` | 是 | - | 上游源系统的原始事件编号/告警主键。 |
| **`tenantId`** | `string` | 否 | `tenant_default` | 租户编码/机构代码。 |
| **`mailbox`** | `string` | 否 | `INBOX` | 归属邮箱文件夹（如 `INBOX`, `SPAM`, `SENT`）。 |
| **`eventTime`** | `string` | 是 | - | 邮件产生/接收时间，**严格使用 ISO-8601 UTC 格式**，例：`2026-11-01T23:55:25Z`。 |
| **`from`** | `string` | 是 | `-` | 规范发件人邮箱（纯邮箱地址，若含展示名应剥离为纯地址）。 |
| **`to`** | `list[string]` | 是 | `[]` | 收件人邮箱列表（**必须为 JSON 字符串数组**，废除逗号分隔字符串）。 |
| **`cc`** | `list[string]` | 否 | `[]` | 抄送人邮箱列表（字符串数组）。 |
| **`replyTo`** | `string` | 否 | `-` | 邮件回复指定地址（Reply-To）。 |
| **`subject`** | `string` | 是 | `-` | 邮件主题。**已完成 RFC 2047 MIME 乱码解码**的纯文本。 |
| **`bodyText`** | `string` | 否 | `-` | 邮件正文的纯文本内容。 |
| **`bodyHtml`** | `string` | 否 | `-` | 邮件 HTML 原生渲染正文（若无可填 `-`）。 |
| **`rawHeaders`** | `string` | 是 | `-` | **完整的 RFC 822 头部纯文本**。以 `\r\n` 或 `\n` 分隔换行，包含 Received 链路、DKIM 签名、SPF 校验等全部事实。 |
| **`senderIp`** | `string` | 是 | `unknown` | 邮件发信 IP 或第一跳外网网关 IP。IPv4/IPv6，缺省填 `"unknown"`。 |
| **`senderHost`** | `string` | 否 | `-` | 发件端 MTA 主机名（HELO/EHLO 声称的主机）。 |
| **`attachments`** | `list[object]` | 否 | `[]` | **结构化附件列表**。每个对象包含：`filename` (文件名), `md5` (32位小写哈希), `size` (字节数整数)。 |
| **`urls`** | `list[string]` | 否 | `[]` | 从正文或头中提取的外链 URL 数组（**规范 JSON 数组**）。 |
| **`securityMeta`** | `object` | 否 | `{}` | 安全特征增强元数据（供大模型与规则引擎直接判断）。下含 `spfResult`, `dkimResult`, `mailHash` 等。 |

## 三、 字段边界约束与最低最高规范 (Field Constraints, Minimums & Maximums)

为防止畸形超大报文拖垮解析器、撑爆 ClickHouse 存储或耗尽内存，接入层必须强制执行以下**最低必须**与**最高容量限额**约束：

### 3.1 最低必须核心字段 (Minimum Required Fields)
任何一封推入系统的邮件，以下 7 个核心字段**必须具备有效内容**（不可缺漏，若缺漏服务端将直接响应 `422 Unprocessable Entity`）：
1. **`eventId`**：全局唯一事件 UUID，用于幂等去重与全链路追踪；
2. **`sourceSystemId`** 与 **`sourceEventId`**：上游来源标识与源端业务编号；
3. **`eventTime`**：事件发生/接收时间戳（ISO-8601 UTC 格式）；
4. **`from`**：合法发件人邮箱地址（单值，提取纯地址）；
5. **`to`**：收件人列表（至少含 1 个收件人）；
6. **`subject`**：邮件主题（无主题填 `"-"`，禁止空值）；
7. **`rawHeaders`**：完整的 RFC 822 报文头（用于溯源链审计与安全认证判定）。

### 3.2 最高工程防护限额 (Maximum Capacity Limits)
上游推送及各组接收端在内存与存储层必须设定的安全容量红线：

| 约束维度 | 最高安全限额 (Hard Cap) | 触发超限处置策略 | 规范设计考量 |
| :--- | :---: | :--- | :--- |
| **单行 Header 最大长度** | `998 字符` | 超出部分强制截断，追加 `header_line_too_long` 标签 | 严格遵循 RFC 5322 单行限制，防止恶意正则回溯 DoS 攻击 |
| **Header 逻辑总行数** | `512 行` | 超过 512 行按尾部截断，追加 `header_block_truncated` 标签 | 防止攻击者恶意构造几千行假 Received 跳撑爆内存 |
| **Header 总字符容量** | `65,536 字符 (64KB)` | 强制截断至 64KB | 报文头最高防御兜底 |
| **Received 跃点总数** | `64 跳` | 仅保留最靠近我方的上层 64 跳，裁撤多余自述跳 | 离我方网关越近的跃点越可信，保护第一跳真实外网源 IP |
| **正文纯文本字符数** | `200,000 字符 (~200KB)` | 截断超出部分，追加 `body_truncated` 标签 | 避免单封大邮件正文撑爆 ClickHouse 单行写性能 |
| **单封附件个数上限** | `100 个` | 最多保留前 100 个附件元数据 | 避免畸形嵌套炸弹 |
| **外链 URL 提取上限** | `1,000 个` | 最多保留前 1000 个唯一链接 | 避免正文内大量垃圾垃圾外链耗尽索引 |
| **单次 HTTP POST 体积** | `16 MB` | 超限直接返回 `413 Payload Too Large` | ASGI / 反向代理层最高防护线 |

### 3.3 缺失与空值纪律 (Null-Safety & Fallback Discipline)
为彻底杜绝各组因类型校验不同造成的 `422` 崩溃，所有字段禁止传 `null`，缺省必须统一填充标准占位符：
- **普通文本类**：缺省统一填 `"-"`（严禁 `null` 或空字符串 `""`）；
- **IP 地址类**：缺省统一填 `"unknown"`（不可与文本的 `"-"` 混用，便于 ClickHouse IP 列索引）；
- **列表数组类**：缺省统一填 `[]`（空数组，严禁填 `null` 或字符串形式的 `"[]"`）；
- **数值与大小类**：缺省统一填 `0`；
- **字典与特征类**：缺省统一填 `{}`。

## 五、 验收与联调指引 (Verification & Self-Testing)

随本规范配套分发的文件：
- **测试数据集**：`mail_offline_dataset_1000.jsonl`（包含 1000 封完全符合本规范定义的脱敏实战邮件，每行一封标准 JSON）
- **灌测客户端**：`bench_push.py`（基于 Python 标准库编写的零依赖压测与联调工具）

### 5.1 本地联调测试步骤
1. 启动本组的邮件接收服务，确保其监听并处理 `POST /api/v2/mails`；
2. 运行 `bench_push.py` 向本地服务推送测试数据（推荐先推送前 100 封进行联调）：
   ```bash
   python bench_push.py --url http://127.0.0.1:8000/api/v2/mails --file mail_offline_dataset_1000.jsonl --limit 100
   ```
3. 检查控制台输出报表：
   - 确认响应状态码全部为 **`HTTP 202`**（成功受理率 100%）；
   - 确认无 `400`、`415`、`422` 或 `500` 报错；
4. 执行全量 1000 封灌测与落库验证：
   ```bash
   python bench_push.py --url http://127.0.0.1:8000/api/v2/mails --file mail_offline_dataset_1000.jsonl --limit 0
   ```
   自测通过后，即可进入后续检索过滤与大模型研判环节。
