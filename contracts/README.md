# 跨模块契约（目标基线）

契约用于独立模块集成，不授予跨模块数据库写权限。当前目录仍是设计说明，**尚无可执行JSON Schema/OpenAPI集成契约**；后续实现需补齐并加入CI。

详细实体与API见[数据与接口设计](../docs/product/数据与接口设计.md)。首批契约：

1. `RawMessageRef`：租户/项目、业务邮件事件ID、原始载荷类型、哈希、来源/采集时间、受控对象引用、完整性。
2. `ParsedMessage`：有序多值头、方言、路由/认证的信任层级、伪造/流向/未知、解析器版本与证据。
3. `MailAnalysis`：各引擎状态/结论/依据、模型及融合策略版本、证据完整性；人工标签另存。
4. `AlertEvent`：外部告警来源、邮件关联及置信度/未匹配原因、命中证据。
5. `RuleCandidate` / `RuleEvaluation`：规则/算法版本、来源样本/反例、冻结数据集与切分、全部指标/失败、审核和有效作用域。
6. 作业/审批事件：任务与尝试、作用域/操作者、进度/终态、审批引用和trace关联。

统一带`schema_version`、租户/项目、生产者/版本、时间和证据引用。总线事件ID与邮件业务event_id分名说明；旧EML的mail_id、Message-ID、内容SHA以及JSON来源幂等键不得混同。旧模块协议由适配层兼容，不反向改成未经迁移的新格式。

`tenant_id`必须来自可信认证上下文，不能把sourceSystemId直接作授权。四类流向码、告警字段等未确认语义仍不猜测；消费者遇到不支持版本明确失败/死信，不悄悄按旧语义执行。

产品交互身份仅`user/admin`两类；来源服务凭据不是第三种登录身份。内部操作上下文须区分真实主体/身份类型和目标作用域：user只限所属租户/资源，admin通过显式管理路径可操作全平台数据；每条写入事件仍带明确归属租户，不用空tenant_id绕过隔离。
