# 工程交付、生产门禁与实施路线图

> v1.1 规划草案 · 以 [综合需求](../综合需求分析.md) 为范围。以下量化值是**建议试点验收起点**，须在容量样本/部署档位确定后冻结；不是当前机器实测，也不是签署的 SLA。

## 1. 分阶段增量交付

| 阶段 | 工作包（按依赖推进） | 可演示结果 | 退出门禁 |
| --- | --- | --- | --- |
| S0 设计基线 | SRS、架构/数据/API、威胁模型、测试/实验协议、ADR、风险/资源台账 | 产品流程/页面原型与契约评审 | 范围/非目标、角色/作用域、现有接口兼容边界明确；未知项有负责人 |
| S1a smart-search 收口 | 新 JSON 容量测试、静态检查遗留、历史回执与幂等保留期、真实模型联通/基线 | 保留独立模块完整链路 | 无模型时真实降级；没有 key 不假定联通完成；JSON 与 EML 分别验收 |
| S1b 产品底座 | React前端/BFF、双模式登录/OIDC、user/admin两类账号、租户/项目、PG/对象/任务、来源/审计/管理员页面、兼容适配 | 两租户用户各自业务闭环；管理员全平台数据读写与管理 | 授权矩阵、持久接入、关键浏览器E2E、原件保护和基本恢复演练 |
| S1c 受控试点 | 容量优化、留存/删除、备份恢复、模型预算、依赖扫描、可观测与运维手册 | 私有网络试点安装包 | 准入环境/数据授权、威胁模型风险闭环、无未修复可利用严重/高危风险、质量与恢复门禁；明确不含后两模块 |
| S2 header-parser | 先标签/可信边界→解析算法→隔离演进/回放→版本审核→证据页面 | 同一邮件的路由/伪造/流向证据增强 | 99%目标口径与分层报告；unknown解释；受控发布/回滚；S1回归通过 |
| S3 threat-trace | 先告警/关联→行为算法→候选规则/反例→回测→审批/影子→命中回流 | 告警到案件再到规则运营闭环 | 泛化报告和原题100%口径；规则沙箱/管理员审核确认；跨模块契约通过 |
| R1 完整生产发布 | 全链路验收、生产拓扑负载、灾备、安全复核、上线/回滚演练、移交 | 完整三模块产品可部署和运营 | 所有纳入范围P0闭环，风险例外有审批且无安全硬门禁豁免 |

主线顺序固定 **smart-search → header-parser → threat-trace**；平台身份/前端/测试和部署伴随每阶段建设，不在最终补壳。各阶段不依赖未来算法才能正常启动。未获取的外部输入仅阻断对应验收，不阻止合成样本/基础工程推进。

**排期原则**：上述是工作包和依赖，不伪造工期。评审后按人员/可用时间、接口联调和外部数据到位日期估算；每两周形成可演示增量，每周同步企业方。新范围需评估容量、安全、验收影响后进 backlog，不直接塞入当前迭代。

## 2. 目标运行档位与容量模型

| 档位 | 用途 | 禁止的宣传 |
| --- | --- | --- |
| Dev / 单机 Compose | 本地开发、契约/E2E、演示与恢复练习；内部端口最小暴露 | 不能以容器自动重启宣称节点级 HA |
| Pilot / 受控试点 | 私有网络、真实授权小规模用户、正式身份/监控/备份；容量限额明确 | 单节点仍须标明单点风险，不签高可用承诺 |
| Production / HA | API/Worker跨故障域，数据库/对象/队列高可用，异地或独立备份、值守 | 复制不是备份，Kubernetes 本身不等于数据可用性 |

生产资源先通过测量确定，不把当前2核小内存开发机当目标。使用变量公式出容量报告：

- 日增事件 `D=100,000` 是当前业务规划输入；平均约1.16条/秒，**不能代表峰值**。测试先用10倍平均（约12条/秒）持续峰值作为暂定值，再用企业真实曲线替换。
- 保留 `T` 天、平均原始大小 `S`：原始逻辑存储 `D×T×S`。例如30天、平均1 MB约3 TB，若两份数据副本约6 TB，尚不含备份、附件额外副本、索引、临时展开和保全数据；这是示例不是实际样本均值。
- 索引按实测字段/压缩比估算；对象、PG/WAL、CH、队列积压、备份、实验中间文件分别预算，预留至少讨论并冻结的安全余量（建议30%起点）。
- 测试同时覆盖大邮件/长正文分位数、附件密度、畸形比例、中文/英文、租户分布；无需等待全量3TB数据即可构建明确标识的负载，但不得把合成负载宣称真实邮件检测集。
- 模型预算 `分析量×平均输入/输出token×单价`，另计重试/多模型；默认按需/初筛后调用，不假设10万封/日全部调用LLM。配额耗尽返回可解释降级。

## 3. 建议 SLO 与验收口径

统一约定：发布前冻结硬件/副本、数据快照、负载脚本、网络、冷/热缓存、观察窗口；从客户端/入口到最终响应计时，排队与超时计入。服务端子阶段指标另报，不替代端到端。

| 对象 | 建议目标 | 测试口径/边界 |
| --- | --- | --- |
| 结构化列表/详情 | P95≤2s，P99≤5s | 30天约300万事件，20并发用户混合读；不是现有109k EML实测的外推 |
| 正文检索 | P95≤5s，P99≤10s | 明确关键词/短语/语言/时间窗及扫描预算，冷热分组；超限明确拒绝 |
| JSON 接收回执 | P95≤1s（≤256KiB合规载荷） | 约12条/秒暂定峰值，含持久化；EML按大小另测，不能回202后丢失 |
| 入索引新鲜度 | 正常负载P95≤10s，P99≤30s | 从 accepted 到可检索；故障积压与恢复排空时间另报 |
| 全栈页面 | 指定测试网络下主要交互页 LCP P75≤2.5s；异步操作及时显示回执/进度 | 冷启动/缓存与375/1440px分别验收，生产静态构建；大任务不阻塞页面 |
| 基础 API 可用性 | HA档月度≥99.9%目标 | 明确纳入的登录/接入/查询/任务API；依赖故障/有效请求超时计失败。测试演练不能代替月度观测 |
| 持续稳定性 | 24h混合负载无 OOM/失控积压，合法请求系统错误率<0.1% | 业务非法请求分开；所有超时/服务拒绝与背压另列，不能剔除后美化 |
| 恢复 | 暂定RPO≤15min、RTO≤4h | 包括证据、状态、密钥、投影与删除台账的可用恢复；必要时在线重建达不到RTO则必须备份索引 |
| 生产安全 | 授权负测零越权，未修复可利用严重/高危风险不发布 | 测试通过不等于绝对无漏洞；中低风险有责任人/期限 |

RPO≤15分钟指灾难场景容许的已确认数据恢复窗口；普通进程重启/网络短故障下已经持久接收的事件必须可对账恢复。若业务要求确认后跨故障域零丢失，需额外冻结同步复制/确认策略并重新压测，不混用两种承诺。LLM耗时/可用性单列，第三方失效不使结构化检索被判成功或整个产品伪装正常。

## 4. 测试与质量流水线

1. **每次提交**：格式/lint、Python/TypeScript类型检查、单元/属性测试、秘密扫描、契约差异。Vite build 不代替 `tsc --noEmit`。
2. **合并请求**：核心模块集成、双租户权限矩阵、真实容器E2E、依赖/SAST/镜像扫描；涉及SQL/下载/外发/沙箱/审批变更需安全审查。
3. **夜间/阶段候选**：真实数据回归、算法基线/消融、负载/资源、worker故障、外部服务降级。付费模型仅在授权且预算允许的专用作业执行，普通CI不外发真实邮件。
4. **发布候选**：新机部署、数据迁移/影子查询、备份恢复、关键浏览器旅程、回滚演练、SBOM/许可证、漏洞与风险评审。
5. **上线后**：合成探测、数据新鲜度/死信、延迟/错误、可用性预算、模型费用/误报漂移；异常触发限流、降级或回滚。

质量报告应包含每项是否实际运行、版本/环境、日志与失败缺口；不允许用“计划增加测试”标为通过。基于当前记录的140项测试、历史旧EML压测、单页浏览器验证均仅是对应模块证据，不等价于本矩阵完成。

## 5. 部署上线与运维清单

### 5.1 环境与构建

- dev/test/staging/prod 身份、凭据、存储、队列完全分开；测试不默认读取生产样本。
- 锁定语言/包/镜像摘要，生成 SBOM；最小镜像、非root、只读文件系统与资源限额；不打包 data/、日志、密钥、缓存进镜像。
- 前端构建静态资源由生产 Web 服务分发，不运行 Vite 开发/preview 服务上线。API 多worker内存与并发按实测配置，数据库迁移只由单独受控步骤执行一次。
- 来源接入/用户统一经TLS入口；8080为内部/本地端口，不直接暴露公网。数据库、扫描器、队列、管理端口位于私网；模型出口经策略代理。
- DNS/证书续期、时钟同步、代理超时、请求大小、CSP/CORS/安全头、日志脱敏均有配置与验证脚本。SPA深层链接刷新、静态资源缓存/版本更新、API路由不互相吞错。

### 5.2 发布/迁移/回滚

- 变更前备份并验证恢复点；数据库按 expand → 兼容发布/回填 → contract 分步，破坏性迁移不能假设镜像回滚能还原数据。
- 先预发布全链路，再灰度指定租户/流量；通过健康、错误、延迟、数据质量和权限信号扩大。
- readiness 检查必要依赖，liveness 不因短暂下游故障造成无限重启；优雅停机停止领取新任务、完成/归还租约，保留回执。
- 回滚触发条件和负责人明确；应用、配置、解析器、规则各有版本回退；涉及不兼容写入时说明数据恢复策略。
- 不自动推送未经批准的规则到企业现网；产品内规则启用与外部邮件系统处置是不同发布对象。

### 5.3 备份、观测与事件响应

- 独立备份PG（含WAL/PITR）、对象与密钥恢复材料、CH必要数据/元信息、配置和删除台账；以完整恢复后的业务对账验证，不只看备份进程exit0。
- 指标：接收成功/拒绝、队列最老年龄/深度、索引延迟、解析partial、扫描未知、查询分位数/超时、模型用量/费用、租户超限、磁盘和备份新鲜度。
- 日志与trace只采集允许字段；审计独立存储/权限/保留，管理员业务数据修改/删除保留操作轨迹，审计历史不可静默篡改；监控标签避免邮箱等PII和无限高基数。
- 告警有级别、值守责任、响应/升级路径和runbook；每种核心故障至少一次演练。事故记录影响范围、时间线、恢复和预防项，涉及数据泄露走企业事件流程。
- 上线前指定运维与安全负责人、维护窗口、补丁周期、退役/数据交付流程；没有责任人不签生产移交。

## 7. 项目治理与完成定义

- 角色责任：产品负责人冻结业务/验收；技术负责人维护ADR/架构；前后端与算法负责人交付实现及证据；测试/安全独立验证；运维负责部署恢复；企业数据负责人确认授权/标签。这些是研发职责而非产品账号类型。产品内仅user/admin两类身份，用户申请由管理员确认；管理员直接操作须安全校验、二次确认和审计，不强制设置第二管理员。
- 每个任务挂需求ID、验收用例、负责人、依赖/风险和交付版本；Definition of Ready 为输入/行为/权限/测试范围明确；Definition of Done 为代码评审、测试证据、契约/文档、迁移/回滚与观测齐备。
- 算法、接口与安全策略变更分别记版本；ADR至少记录背景、候选、决定、代价、证据和重新评估条件。
- 发布门禁：P0功能完整、关键流程E2E通过、跨域权限与提示注入/沙箱边界通过、数据迁移/恢复/性能达标、算法达到已冻结P0指标、运维与许可证材料齐备。未达到算法P0指标时，须经企业方书面重新划定交付范围/版本并更新需求和验收；不能单方用“受限版本”说明绕过R1门禁，安全硬约束不得以范围说明豁免。
- 如果真实模型/企业标签/生产环境尚未具备，交付名称必须是“开发验证版/受控试点版”，不能以文档齐全或mock通过宣布完整Production-Ready。
