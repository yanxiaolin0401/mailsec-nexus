# MailSec Nexus：项目目标与顶层约束

> v1.1 · 2026-10-22。系统级产品要求已升级；完整需求以[综合需求分析](综合需求分析.md)为准。本文是共同约束摘要，不是生产验收通过证明。

## 1. 产品目标与开发顺序

建设面向企业安全运营的**邮件智能检测、调查与规则运营产品**：授权数据接入 → 证据保全 → 大规模检索/模型辅助研判 → 案件复核 → 头部可信解析增强 → 行为分析/规则回测 → 审核发布与反馈。

交付不是三个算法页面拼接，而是前后端分离、租户/项目与用户隔离、管理员后台、全栈业务流程、可评测算法、可安装升级及运维的工程系统。

**顺序固定：smart-search → header-parser → threat-trace。** 平台身份、前端、测试和部署随阶段迭代。smart-search 继续可独立运行，其基础解析不依赖未完成的 header-parser；后续通过版本化契约接入增强能力。

| 阶段 | 产品能力 | 必需产物 |
| --- | --- | --- |
| S1 | smart-search收口与产品底座：接入、搜索、研判、案件、身份/隔离/管理 | 独立模块、正式前端/API、数据/权限契约、质量证据、受控试点部署 |
| S2 | 多方言头部解析、可信链、伪造/流向、解析器演进 | 确定性Python算法、样本/标签、隔离回放/评测、证据页、审核回滚 |
| S3 | 告警关联、行为挖掘、候选检测规则、泛化回测 | 检出算法及说明、实验/反例、规则审核/影子运行、命中回流 |
| R1 | 完整生产产品 | 跨模块E2E、容量/安全/恢复验收、安装升级/运维移交 |

## 2. 不可绕过的约束

| ID | 约束 |
| --- | --- |
| C01 架构边界 | 平台管共享身份/流程/案件/审计，模块管领域算法；可独立测试发布，不互写彼此私有业务表。 |
| C02 兼容契约 | 保留smart-search已冻结JSON/EML入口、幂等和未知语义；跨模块契约含作用域/版本/生产者/证据；不静默破坏接口。 |
| C03 证据 | 原始JSON/EML/附件字节与派生结果分层；保留哈希、来源、采集链、有序多值头。没有原件字节不伪称已扫描。 |
| C04 信任 | 报文声称、可信网关观测和本系统重新验证分别标注；证据不足拒判，不声称真实攻击者身份。 |
| C05 AI/执行 | 邮件是不可信内容；模型不能直通SQL/shell/任意URL。生成代码/规则必须隔离评测、审核发布；线上解析确定性运行。 |
| C06 数据治理 | 真实数据处理/外发有授权与最小化策略、地域/留存/删除/保全；脱敏不等于完全匿名；凭据不入仓库/日志。 |
| C07 租户/用户 | 仅平台用户和后台管理员两类身份；用户按租户/资源隔离，管理员经后台授权路径全平台读写；sourceSystemId不是租户认证。 |
| C08 管理权限 | 管理员拥有最高平台操作与全部租户数据读写权。登录页区分用户租户/管理员模式，模式不能授予权限；高风险操作二次确认并审计，不另设租户管理员或审核角色。 |
| C09 可靠性 | 202仅表示持久接收；处理有界、重试幂等、死信可查、状态对账。unknown/partial/故障不可当成功或安全。 |
| C10 评测 | 冻结标签、分母、切分和版本；独立留出、基线/消融、误报/漏报/未知/成本完整报告；模拟不替代实测。 |
| C11 发布 | 版本和审批可追溯、可回滚；灰度、备份恢复、新机部署和浏览器全栈测试通过才上线。 |
| C12 生命周期 | 数据删除先阻断可见性再物理清理，对缓存/导出/备份恢复重放；法律保全/副本限制明示。 |
| C13 安全执行 | 静态扫描、解析隔离、生成代码沙箱与动态恶意附件沙箱分开；Docker/ClamAV不自动等于强动态沙箱。 |
| C14 可交付 | 依赖/镜像锁定、SBOM/许可证、CI、审计、运维责任、漏洞响应与交付文档齐备；不虚称合规认证。 |

## 3. 范围裁定与指标

- 当前主接入为HTTP8080嵌套JSON，EML兼容；生产经TLS入口，不实现SMTP网关/自动拦截。
- ClickHouse继续邮件检索主引擎；PG/对象存储/持久队列是平台产品建设，不推翻模块独立版约束。不要求Elasticsearch DSL；历史ES只读适配按S2数据需求决定。
- 统一React+TypeScript前端是产品目标；既有轻量Web仍为独立模块有效成果，但不能替代正式平台。
- 99%伪造/流向目标、99%解析服务可用性以及规则100%目标分别定义口径；不得把有限集零误报外推未来。系统HA档99.9%是另列的拟议SLO，不混同原题指标。
- 10万封/日为容量规划输入，现有EML批导报告不是JSON持续吞吐证明。具体量化建议和冻结流程见[交付路线图](product/工程交付与实施路线图.md)。

原始课题和企业细则仍保留在模块目录。新的产品级要求以本次用户决定和综合需求裁定为准；算法/协议细节在不冲突时继续遵守模块文档。待确认输入仅阻断对应阶段验收，见[资源台账](资源需求与待确认事项.md)。
